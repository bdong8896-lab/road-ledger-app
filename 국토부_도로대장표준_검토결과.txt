1. 가장 중요한 발견 — 이 표준의 "정체"부터 재확인
--------------------------------------------------------
문서를 실제로 읽어보니, 이 4종 문서는 "우리 소프트웨어가 내부적으로 이 구조를
그대로 써야 한다"는 규격이 아니라, **각 도로관리청(시·군·구 등)이 도로법
제56조에 따라 최종적으로 국토교통부의 '도로대장 통합관리체계'(과도기에는
'도로대장정보시스템 KRRIS')에 제출해야 하는 산출물(성과품) 포맷 규정**입니다.

업무매뉴얼 제5장("자체시스템으로 관리하는 도로대장의 전환")에 정확히 우리
상황이 나옵니다:
  - 도로관리청이 자체시스템(=지금 만들고 있는 이 웹앱)에서 도로대장을 관리
    하는 경우, 표준 형식으로 "전환"할 수 있다.
  - 절차: 발주 준비 → (외부 "도로대장 작성업체"가) 정위치 편집·구조화 편집·
    품질검수 수행 → 도로관리청 검수(논리오류검수) → KRRIS 제출 → 등재 확인.

즉, 지금 만들고 있는 시스템은 표준 문서가 말하는 "자체시스템"에 정확히
해당하고, 이 자체시스템이 49개 테이블 구조를 내부에 그대로 가지고 있을
필요는 원래 없습니다. 실제 KRRIS 제출 시점에 별도 변환 작업(대개 외주 용역)을
거쳐 표준 포맷으로 뽑아내면 되는 구조입니다. 그런 의미에서, 지난 세션에 미리
만들어둔 gov_facility_schema.sql(49개 테이블 전체, 국토부 정의서 그대로)은
이 "미래의 변환 작업"을 위한 선제적 준비물로 봐도 됩니다 — 당장 필수는
아니었지만 유용한 대비입니다.

2. 새로 확인된 표준의 세부 규칙 (이전 검토엔 없던 내용)
--------------------------------------------------------

(1) RDID(시설물 관리 아이디, 27자리) 구성 규칙
    레이어분류(3) + 도로등급코드(4) + 관리기관번호(5) + 노선번호(4)
    + 구간번호(3) + 부여연도(4) + 일련번호(4) = 27자리

    예시: R02150216100001801120230001
      R02(교량) / 1502(일반국도) / 16100(관리기관) / 0018(18호선)
      / 011(11구간) / 2023(부여연도) / 0001(일련번호)

    → "레이어분류"는 엑셀에 있던 8자리 레이어코드(예: A0070000)와는 다른,
      R + 테이블번호 2자리로 된 별도의 짧은 코드입니다(R01=총괄, R02=교량...).
      우리 gov_facility_schema.sql의 각 테이블 PK는 그냥 VARCHAR(27)로만
      열어뒀을 뿐, 이 생성 규칙 자체는 아직 구현하지 않았습니다.

(2) 도로등급은 텍스트가 아니라 코드값
    RDID 예시에서 보듯 "일반국도"가 아니라 "1502"라는 4자리 코드로 저장됨
    (공통입력코드정의서 v2.6에 전체 코드 있음). **우리 road_ledger.road_grade는
    지금 "군도", "시도" 같은 한글 텍스트를 그대로 저장**하고 있어 이 부분은
    표준과 다릅니다. 노선번호·구간번호도 마찬가지로 표준은 숫자 코드
    (4자리/3자리)인데, 우리 route_no/sect는 자유 텍스트 입력창입니다.

(3) 시점/종점 필드의 정확한 의미 — 지난 검토에서의 오해 정정
    총괄(01) 테이블의 "위치-시점/위치-종점"은 **번지 단위까지의 주소 텍스트**
    입니다(작성지침 예시: "경기도 고양시 관산동 876-2번지"). 지난 세션에
    해남군 화면 캡처에서 본 "0.000Km~0.730Km" 표기를 보고 "시점/종점이 Km
    단위 거리여야 하는데 우리는 텍스트로 저장 중"이라고 판단했었는데, 이건
    제 착오였습니다 — **우리가 지금 start_point/end_point에 주소 텍스트를
    저장하는 방식이 오히려 표준과 맞습니다.**

    Km 단위 거리는 총괄 테이블이 아니라, 개별 시설물(교량·정차대·측구 등)의
    "위치-시점/종점" 필드에서 쓰입니다 — 그 구간의 시점을 0으로 두고 몇 m
    지점에 그 시설물이 있는지를 나타내는 값(NUMERIC, 단위 m)입니다. 이미
    gov_bridge, gov_stopbay 등 시설물 테이블들의 sect_st/sect_ed 컬럼이
    정확히 이 방식(NUMERIC)으로 만들어져 있어서, 이 부분은 이미 올바르게
    반영돼 있습니다.

(4) 도로대장 = "공간정보"(49개 레이어, SHP) + "기타정보"(구조물도면 PDF,
    표지사진 JPG). 파일명 규칙: 관리기관(5)+노선(4)+구간(3)+점선면구분(3)
    +레이어코드(8). 우리 route_files(도면/도면종류/구조물/공사도면/동영상
    탭)가 개념적으로 이 "기타정보" 첨부와 상통합니다.

(5) 도로법 제10조가 정의하는 적용대상 도로: 고속국도·일반국도·특별시도·
    광역시도·지방도·시도·군도·구도 — 8종. 우리가 쓰는 9종(+'기타')과
    정확히 일치합니다(전에 이미 이걸 기준으로 도로등급 목록을 수정해뒀음).

3. 현재 시스템 구조 대비 정리
--------------------------------------------------------

[이미 잘 반영된 부분]
  - 도로등급 9종 목록: 도로법 제10조 적용범위와 정확히 일치
  - 관리기관(MCO) 368개 코드 이미 반영 (관리기관 입력창 자동완성)
  - 부속시설 22종 포함, 국토부 정의서 49개 테이블 전체를 별도 스키마로
    구축 완료(gov_facility_schema.sql) — 필드명·자료형·길이·필수여부까지
    원본과 1:1 대응
  - 시설물 단위 위치(m 단위 NUMERIC)와 총괄 단위 위치(주소 텍스트)의
    구분이 스키마에 정확히 반영됨
  - 노선 단위 파일첨부(route_files)가 "공간정보 외 기타정보" 개념과 상통

[부분적으로만 맞음 / 개선 여지]
  - road_grade·route_no·sect가 자유 텍스트 입력 — 표준은 코드/숫자 기반.
    지금 방식은 오탈자로 같은 노선이 트리에서 갈라져 보이는 위험이 있음
    (이전에 설명드렸던 한계와 같은 원인)
  - 시점/종점을 "번지 단위까지" 입력하도록 안내 문구를 폼에 추가하면
    표준과의 정합성이 더 좋아짐 (지금은 형식 제약이 없음)

[구조적으로 다른 부분 — 표준을 그대로 따르려면 재설계 필요]
  - 우리 road_ledger는 필지(PNU) 단위가 최상위 키. 표준은 노선/구간
    단위(01.총괄, RDID가 PK)가 최상위 — "노선"이 우리 시스템에선 독립
    레코드가 아니라 필지들을 노선번호/노선명으로 묶은 파생 개념일 뿐임
    (이전 세션에서 설명드린 부분, 이번 문서 검토로 재확인됨)
  - RDID 27자리 생성 규칙 미구현 — gov_* 테이블 PK는 문자열 칸만 열려있고
    실제 자동 채번 로직은 없음
  - 도로등급/노선번호/구간번호의 텍스트→코드 매핑 미구현

4. 결론 및 제안
--------------------------------------------------------
표준 문서 자체가 "자체시스템으로 관리하다가 필요 시 변환해서 제출"하는
경로를 정식 절차로 인정하고 있으므로, 지금 구조(필지 기반, 자유 텍스트
노선/등급)는 표준 위반이 아니라 문서가 예정하고 있는 정상적인 사용
시나리오입니다.

다만 실제로 KRRIS(또는 향후 도로대장 통합관리체계)에 데이터를 제출해야
하는 시점이 오면, 그때 아래 "전환 작업"이 필요합니다:
  1) 노선/구간을 총괄테이블 개념의 독립 레코드로 승격
  2) 도로등급·노선번호·구간번호를 코드값으로 매핑
  3) RDID 27자리 자동 채번 로직 추가
  4) (필요시) 실제 시설물 데이터를 gov_* 49개 테이블에 입력/수집

이건 지금 당장 처리할 필요는 없고, 실제 제출 요구가 생겼을 때 별도
작업으로 진행하면 되는 부분입니다. 지금 시스템은 일상적인 도로대장
관리(필지별 정보 입력, 도면 관리, 지도 조회) 용도로는 문제없이 쓸 수
있는 구조입니다.
