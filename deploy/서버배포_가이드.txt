0. 사전 준비 (서버에 이미 되어 있어야 하는 것)
--------------------------------------------------------
⚠ 아래는 이전 서버(192.168.0.211) 기준 체크리스트를 그대로 옮겨온 것이다.
105.24.1.170은 IT팀이 "서버 자원 할당, OS, IP, 계정 설정"만 완료했다고
안내했고(원격데스크톱 포트 33890, administrator 계정), Node.js/IIS/SFTP는
실제로 설치·확인된 게 아니다. PostgreSQL은 처음엔 `Get-Service -Name
postgresql*`로 확인했을 때 아무것도 안 나와 미설치로 판단했었으나(2026-09-14),
이후 이미 설치돼 있는 것으로 확인됨 — 포트/계정 정보를 모르는 상태라 아래
"PostgreSQL 포트·계정 확인" 절차로 직접 알아내야 한다.
아래 항목들은 이번 배포 과정에서 우리가 직접 새로 설치/확인해야 한다.

- PostgreSQL: 이미 설치돼 있음(설치 자체는 안 해도 됨). 포트/계정 정보를
  모르니 바로 아래 "PostgreSQL 포트·계정 확인" 절차부터 진행할 것
- Node.js 설치 필요 (미확인 — 서버 접속 후 `node -v`로 먼저 확인할 것)
- IIS는 이미 설치돼 있음(8080 포트에서 다른 시스템이 이미 서비스 중 —
  건드리지 말 것). 우리 몫은 아래 두 확장 모듈이 설치돼 있는지 확인 후, 같은
  IIS에 "새 사이트"를 11800 포트로 추가하는 것:
    1) URL Rewrite       (https://www.iis.net/downloads/microsoft/url-rewrite)
    2) Application Request Routing, ARR  (https://www.iis.net/downloads/microsoft/application-request-routing)
  설치 후: IIS 관리자 → 서버 최상위 노드 선택 → 가운데
  "Application Request Routing Cache" 더블클릭 → 우측
  "Server Proxy Settings..." → Enable proxy 체크 → Apply
  (이거 안 하면 리버스프록시가 502를 반환함)
- 방화벽 인바운드 11800 포트 허용 필요 — 보안팀에 요청 완료(원격접속 포트
  33890 이외의 포트는 "서버 작업 시 보안팀과 협의"하라는 안내를 받음).
  서버 관리자 권한이 있다면 직접 등록도 가능(3000, 5432는 외부 노출 금지 —
  로컬 전용):
     New-NetFirewallRule -DisplayName "RoadLedger-11800" -Direction Inbound -Protocol TCP -LocalPort 11800 -Action Allow
- SFTP: 이전 서버는 FreeSFTPd(Dsuser 계정, Home Directory D:\)를 썼다. 새
  서버에 SFTP가 준비돼 있는지 미확인 — 없다면 원격데스크톱(포트 33890)으로
  직접 접속해 파일을 올리거나(예: 공유폴더, 복사-붙여넣기), FreeSFTPd를 새로
  설치하는 방법이 있다. 확인 후 이 섹션을 실제 값으로 갱신할 것.

  ● PostgreSQL 포트·계정 확인 (원격데스크톱 105.24.1.170:33890 접속 후, PowerShell)

    1) 서비스 확인 — 이름이 "postgresql"로 안 시작할 수도 있으니 넓게 검색:
         Get-Service | Where-Object { $_.DisplayName -like "*postgres*" }
       DisplayName에 보통 버전이 포함돼 있다(예: "postgresql-x64-16").

    2) 설치 경로·데이터 폴더 확인:
         Get-ChildItem "C:\Program Files\PostgreSQL" -ErrorAction SilentlyContinue
       버전 폴더(예: ...\PostgreSQL\16\)가 나오면 그 안 data\postgresql.conf가
       설정 파일이다.

    3) 실제 포트 확인 — 설정 파일에서 직접 읽거나:
         Select-String -Path "C:\Program Files\PostgreSQL\<버전>\data\postgresql.conf" -Pattern "^port"
       또는 실제 리스닝 포트를 프로세스 기준으로 바로 확인(더 확실함, 설정
       파일과 실제 구동 포트가 다를 수 있음):
         Get-NetTCPConnection -OwningProcess (Get-Process postgres).Id | Select-Object LocalPort

    4) 계정/비밀번호 — 기존 비번을 "알아내는" 방법은 없다(해시로만 저장됨).
       모르면 우리 앱 전용 계정을 새로 만드는 게 제일 안전하다(기존 계정·데이터는
       전혀 건드리지 않음):

       a) data\pg_hba.conf를 열어 "local"/"127.0.0.1" 인증 방식(보통
          scram-sha-256 또는 md5)을 적어두고(되돌릴 때 필요) 임시로 trust로 변경
          (반드시 원본을 복사해서 백업해둘 것)
       b) 서비스 재시작:
            Restart-Service <1번에서 확인한 서비스 이름>
          ⚠ 이 재시작 순간 그 PostgreSQL을 쓰는 기존 시스템(있다면)의 DB 연결도
          잠깐 끊긴다 — 운영 영향 적은 시간대에 진행할 것
       c) 비밀번호 없이 접속:
            & "C:\Program Files\PostgreSQL\<버전>\bin\psql.exe" -U postgres -h 127.0.0.1 -p <2번에서 확인한 포트>
       d) 우리 앱 전용 계정·DB 생성:
            CREATE USER "DSMap" WITH PASSWORD '원하는비번';
            CREATE DATABASE "DSMap" OWNER "DSMap";
       e) pg_hba.conf를 a)에서 적어둔 원래 인증 방식으로 되돌리고 서비스 재시작
       f) 새 계정으로 재접속해서 확인:
            & "C:\Program Files\PostgreSQL\<버전>\bin\psql.exe" -U DSMap -h 127.0.0.1 -p <포트> -d DSMap

       확인된 포트·계정을 아래 3-2 스키마 적용 절차와 server/.env.production의
       PGPORT/PGUSER/PGPASSWORD에 그대로 반영할 것(포트가 5432가 아니면 그 값
       그대로 쓰면 됨 — 굳이 5432로 바꿀 필요 없음).

업로드 대상 서버 경로: D:\Dsmap_ROAD  (SFTP 접속 시엔 "/Dsmap_ROAD"로 보임)

  - .vscode/, README.md    → 없어도 동작에 지장 없음 (참고용)

3. 서버에서 실행할 것 (원격 데스크톱으로 105.24.1.170:33890 접속 후)
--------------------------------------------------------
SFTP는 파일만 옮길 뿐 명령을 실행하지 못하므로, 아래는 반드시 서버에 RDP로
직접 접속해서 PowerShell(관리자 권한 권장)로 실행해야 함. 원격 데스크톱
연결 시 컴퓨터 입력란에 "105.24.1.170:33890"처럼 포트를 콜론으로 붙여서
입력할 것(포트가 기본값 3389가 아니라 33890으로 변경돼 있음), 계정은
administrator.

  1) 파일명 변경
     D:\Dsmap_ROAD\server\.env.production → .env 로 이름 변경
     (PowerShell: Rename-Item "D:\Dsmap_ROAD\server\.env.production" ".env")

  2) PostgreSQL 스키마 적용 — 기본 스키마 + 일괄등록(SHP/DBF)용 정부표준
     시설물 테이블 49종(gov_road_bound 등) 둘 다 적용해야 함. 후자를 빠뜨리면
     일괄등록 시 "OOO 이름의 릴레이션(relation)이 없습니다" 에러가 남.

     ※ psql 실행 시 실제로 겪은 문제 2가지 — 아래 표준 절차로 한 번에 예방:

       (a) "psql: 용어를 찾을 수 없습니다"(CommandNotFoundException)
           → PostgreSQL 설치는 됐지만 psql.exe가 PATH에 없는 경우. 전체
             경로로 직접 실행하면 됨(버전 번호는 서버에 설치한 실제 버전으로
             — 105.24.1.170은 이번에 새로 설치하는 것이라 설치 시 고른 버전을
             그대로 쓸 것, 이전 서버는 18이었음). 안 보이면 먼저 찾기:
               Get-ChildItem "C:\Program Files\PostgreSQL" -Recurse -Filter psql.exe

       (b) "OOO와 대응되는 문자(인코딩: "UHC")가 없습니다" — 한글이 깨져서
           CREATE/ALTER 문이 무더기로 실패(뒤이은 문장들도 "테이블이 없다"고
           연쇄로 실패함)
           → Windows 한국어 로케일 때문에 psql이 UTF-8로 저장된 스크립트를
             UHC(CP949 계열)로 잘못 해석해서 생김. 아래처럼 클라이언트
             인코딩을 UTF8로 강제 지정하면 됨.
           ⚠ PowerShell 변수는 $ 기호(달러)로 시작한다. &(앰퍼샌드)로
             잘못 치면 "CommandNotFoundException"만 뜨고 인코딩 설정은 조용히
             적용되지 않은 채로 넘어가서, 뒤에서 다시 (b) 오류가 재발한다 —
             $env:PGCLIENTENCODING 앞에 반드시 $인지 확인.

     표준 절차(매번 이 순서로) — 아래 "18"은 이전 서버(192.168.0.211) 기준
     예시일 뿐, 105.24.1.170에 실제로 설치한 PostgreSQL 버전 번호로 바꿔서
     실행할 것(설치 시 고른 버전 그대로):
     $env:PGCLIENTENCODING = "UTF8"
     & "C:\Program Files\PostgreSQL\18\bin\psql.exe" -h localhost -p 5432 -U DSMap -d DSMap -f D:\Dsmap_ROAD\server\db\schema.sql
     & "C:\Program Files\PostgreSQL\18\bin\psql.exe" -h localhost -p 5432 -U DSMap -d DSMap -f D:\Dsmap_ROAD\server\db\gov_facility_schema.sql

     두 파일 다 CREATE TABLE/ALTER TABLE이 전부 IF NOT EXISTS라서, 중간에
     실패했더라도(예: 인코딩 문제로) 원인 해결 후 그냥 다시 실행하면 안전하게
     이어서 완성된다 — 되돌리거나 DROP할 필요 없음.

  3) Node 패키지 설치 + 관리자 계정 생성
     cd D:\Dsmap_ROAD\server
     npm install --omit=dev
     node db/seed-admin.js <아이디> <비밀번호> <표시이름>

  4) PM2로 상시 구동 등록 (최초 1회는 PM2/시작프로그램 등록도 필요)
     npm install -g pm2 pm2-windows-startup      (최초 1회만)
     pm2-startup install                          (최초 1회만, 재부팅 시 자동시작 등록)
     cd D:\Dsmap_ROAD\server
     pm2 start ecosystem.config.js
     pm2 save

     * 이후 코드를 새로 배포하면: pm2 restart road-ledger
     * 로그 확인: pm2 logs road-ledger --lines 50
     * ⚠ 실제로 겪은 문제 — 재부팅했더니 pm2 list에서 등록해둔 앱이 통째로
       사라짐. pm2는 재부팅 시 무조건 되살아나는 게 아니라 "저장해둔 목록"만
       되살리는 방식이라, pm2 start/restart로 뭔가 바꿀 때마다 매번
       pm2 save까지 해야 한다(start만 하고 save를 안 하면 다음 재부팅 때
       그 변경이 사라짐). 재발하면 pm2-startup install이 제대로 등록됐는지도
       재확인(pm2 startup 실행해서 안내 다시 따라가기, 또는 작업 스케줄러에서
       "PM2"로 검색해 해당 작업이 있는지 직접 확인).

  5) IIS에 새 사이트 생성 (최초 1회) — IIS 자체는 이미 설치돼 있고 8080 포트에
     다른 시스템이 떠 있으니, 그 사이트는 절대 건드리지 말고 "사이트 추가"로
     별도 사이트만 새로 만들 것
     - 포트: 11800
     - 물리 경로: D:\Dsmap_ROAD  (web.config가 이 폴더 최상위에 있어야 함)
     - 사이트 선택 → 가운데 "인증(Authentication)" → 익명 인증 = 사용(Enabled),
       Windows 인증 = 사용 안 함(Disabled)  ← 이거 안 하면 401 오류남
     - NTFS 권한: D:\Dsmap_ROAD 폴더에 IIS_IUSRS 그룹 읽기/실행 권한 부여
         icacls "D:\Dsmap_ROAD" /grant "IIS_IUSRS:(OI)(CI)RX" /T

  6) 접속 테스트
     브라우저에서 http://105.24.1.170:11800 접속 → 로그인 화면 확인
     → 로그인 시도까지 정상 동작하는지 확인 (안 되면 아래 4번 트러블슈팅 참고)

    안 보이면 Get-ChildItem "C:\Program Files\PostgreSQL" -Recurse -Filter psql.exe

[증상] psql로 schema.sql/gov_facility_schema.sql 적용 시 한글이 깨져서
       "OOO와 대응되는 문자(인코딩: "UHC")가 없습니다" 대량 오류, 그 여파로

  → Windows 한국어 로케일 때문에 psql이 UTF-8 스크립트를 UHC(CP949)로 잘못
    해석해서 생김. 수정 코드(재시도 전에 먼저 실행, $ 기호 꼭 확인 — &로
    잘못 치면 조용히 무시되고 이 오류가 재발함):
      $env:PGCLIENTENCODING = "UTF8"
    IF NOT EXISTS 기반이라 실패한 psql 명령 그대로 재실행하면 안전하게 이어서
    완성됨.

[증상] 사이트 접속 시 "401 - Unauthorized: Access is denied due to invalid
       credentials"
  → IIS 인증 설정 문제. 3-5)의 익명 인증 활성화(IIS 관리자 GUI로 설정,
    스크립트화하지 않음 — 사이트명이 서버마다 달라 명령으로 잘못 건드리면
    다른 사이트에 영향 줄 수 있어 위험) + NTFS 권한 수정 코드:
      icacls "D:\Dsmap_ROAD" /grant "IIS_IUSRS:(OI)(CI)RX" /T
    이 오류는 URL Rewrite가 동작하기도 전에 IIS 인증 단계에서 막히는 것이므로
    web.config 내용과는 무관함.

[증상] 로그인 화면(정적 페이지)은 뜨는데 로그인(아이디/비번 입력 후 제출)이
       안 됨
  → 정적 파일은 잘 서빙된다는 뜻이므로 IIS↔Node 리버스프록시 자체는 정상.
    문제는 POST 요청(/api/auth/login) 쪽. 아래 순서로 원인 확인:
    1) 브라우저 F12 → Network 탭 → 로그인 재시도 → "login" 요청의
       상태 코드/응답(Response) 확인
         - 상태코드 500이면 → 서버(Node) 쪽 에러. 아래 pm2 logs 확인
         - 상태코드 405/501 등이면 → IIS의 WebDAV 모듈이 POST 요청을 가로채는
           경우가 있음. IIS 관리자에서 해당 사이트의 "모듈(Modules)" 또는
           "핸들러 매핑"에서 WebDAVModule 제거/사용 안 함으로 설정
         - Network 탭에 요청 자체가 안 뜨면 → Console 탭에서 JS 에러 확인
    2) 서버에서 pm2 logs road-ledger --lines 50 실행 → 로그인 시도 시
       에러가 찍히는지 확인. 특히:
         - "password authentication failed" → .env의 PGPASSWORD가 실제
           PostgreSQL DSMap 계정 비밀번호와 다름. 수정: .env의 PGPASSWORD를
           고친 뒤 pm2 restart road-ledger
         - "ECONNREFUSED" → PostgreSQL이 5432에서 안 열려있거나 로컬 접속을
           막고 있음. 서비스 상태 확인:
             Get-Service -Name postgresql*
           멈춰있으면: Start-Service -Name <위에서 확인한 서비스명>
           (그래도 안 되면 pg_hba.conf, listen_addresses 설정 확인 필요)

[증상] WinSCP로 특정 폴더(Dsmap_ROAD)만 "No such file" 오류로 접속 안 됨
  → 폴더가 실제로 없거나(먼저 만들어야 함), FreeSFTPd에서 그 계정(Dsuser)에게
    해당 경로 접근 권한이 없는 경우. FreeSFTPd 관리자 프로그램에서 Dsuser의
    Home Directory 설정과 권한을 직접 확인. Windows NTFS 권한을 준 것과는
    별개의 문제일 수 있음.

[증상] web.config에 <security><requestFiltering>나 <serverRuntime
       uploadReadAheadSize>를 추가한 뒤 사이트 전체가 "HTTP 오류 500.19 -
       Internal Server Error"(오류 코드 0x80070021)로 완전히 죽음(정적 파일도
       API도 전부 안 뜸)
  → 실제로 겪은 문제. 서버 레벨(applicationHost.config)에서 해당 구성 섹션이
    잠겨있으면(locked, overrideModeDefault="Deny") web.config가 그 섹션을
    오버라이드하려는 순간 사이트 전체가 이 에러로 죽는다. 이 서버는
    requestFiltering과 serverRuntime 둘 다 잠겨있었다(하나씩 시도하며 확인).
    조치 순서:
      1) 즉시 복구 — web.config에서 문제의 섹션을 빼고 리라이트 규칙만 남겨서
         재업로드(재시작 불필요, 바로 반영). 현재 deploy/web.config가 바로 이
         상태(맨 위 주석에 원래 설정이 남아있음).
      2) 잠금을 풀려면(관리자 PowerShell, appcmd 자체는 서버 레벨 도구라
         PATH 걱정 없이 전체경로로 실행):
           & "C:\Windows\System32\inetsrv\appcmd.exe" unlock config -section:system.webServer/security/requestFiltering
           & "C:\Windows\System32\inetsrv\appcmd.exe" unlock config -section:system.webServer/serverRuntime
         ⚠ %windir%는 PowerShell에서 자동으로 안 풀린다(cmd 문법) — 위처럼
         전체경로나 $env:windir를 써야 함. -section: 뒤는 반드시 슬래시(/)이지
         백슬래시(\)가 아님(system.webServer/security/requestFiltering).
      3) 잠금 해제 확인되면 하나씩만 살려서 재적용 + 매번 사이트 확인(한 번에
         다 넣지 말 것 — 또 죽으면 어느 게 원인인지 못 찾음).
    현재 상태(2026-09-01): requestFiltering은 unlock 성공 확인 후
    maxAllowedContentLength(업로드 용량 500MB — multer의 fileSize 제한과
    통일함, bulkImport.js)만 재적용함 — 정상 작동 확인.
    serverRuntime(uploadReadAheadSize)은 잠금 해제를 안 했고 web.config에도
    없음. 남은 제한:
      - GET /api/parcels?pnus=... 의 URL 길이(maxQueryString/maxUrl, 같은
        requestFiltering 섹션이라 잠금은 이미 풀려있음, 필요하면 web.config
        맨 위 주석대로 requestLimits에 속성만 추가): 지도 많이 축소 시 414로
        필지 색칠 일부 실패 가능(치명적 아님, 확대하면 정상)
      - ARR 프록시 업로드 버퍼(uploadReadAheadSize, serverRuntime 잠금 미해제
        상태): 매우 큰 파일을 웹으로 직접 올릴 때 maxAllowedContentLength만으론
        부족하면 이게 필요할 수 있음 — 필요해지면 위 2)의 serverRuntime unlock
        먼저 확인 후 추가할 것

[증상] 일괄등록(검수 시작)이나 큰 파일 업로드 시 "Unexpected token '요', ...
       is not valid JSON" 에러
  → JSON 파싱 에러처럼 보이지만 실제론 IIS가 응답한 HTML 에러 페이지("요청
    엔티티가 너무 큽니다")를 프론트가 JSON으로 파싱하려다 실패한 것. IIS의
    기본 업로드 제한(maxAllowedContentLength, 기본 약 28.6MB)을 넘는 파일이라
    Node까지 가지도 못하고 IIS 단계에서 거절된 것이 원인.
    2026-08-28 requestFiltering 섹션 잠금 해제 확인 후 web.config에
    maxAllowedContentLength를 재적용해 해결됨(위 "500.19" 항목 참고 — 값은
    2026-09-01에 multer의 fileSize 제한과 통일하기 위해 524288000(500MB)으로
    재조정됨). 그래도 이 에러가 다시 나면 ARR 프록시 버퍼(uploadReadAheadSize,
    serverRuntime — 아직 잠금 미해제)가 필요한 경우일 수 있음.
    당장 큰 파일을 올려야 하는데 위 방법이 막히면, 이 제한 자체를 우회하는
    섹션 5의 SFTP 사전 업로드 방식(A/B)을 쓰는 게 더 안전하다 — 웹 업로드
    용량과 무관하게 동작함.

[증상] public-dist(난독화 빌드) 대신 public/(원본)이 서빙되는 것 같음
  → .env에 SERVE_DIR=public-dist 줄이 빠져있으면 config.js 기본값(public)으로
    떨어짐. D:\Dsmap_ROAD\server\.env에 SERVE_DIR=public-dist가 있는지, 그리고
    D:\Dsmap_ROAD\public-dist 폴더 자체가 실제로 업로드돼 있는지 확인. 수정 후

    읽으므로 재시작해야 반영됨).

[증상] 배포 후 지도/지적도가 안 뜸 (VWorld 타일 401/403)
  → VWorld 키는 서비스 URL(스킴/IP/포트)이 정확히 일치해야 동작한다.

      키: <발급받은 VWorld 키 — 값은 server/.env.production에만 둠>

    실제 접속 주소(스킴/포트 포함)와 정확히 일치하는지, 키 상태가 "승인"인지
    확인.

5. 일괄등록(SHP/DBF) 시 대용량 파일(사진/보고서/도면) 사전 업로드
--------------------------------------------------------
일괄등록 웹 화면(zip 업로드)은 IIS 업로드 제한 때문에 사진·보고서·CAD
도면처럼 용량이 큰 파일을 매번 함께 올리면 부담이 크다. 그래서 SFTP로 서버에
미리 올려두는 두 가지 방식을 지원한다("일괄등록" 화면 상단 탭으로 전환).

  [방식 A] ZIP(또는 폴더) 업로드 + 사전 업로드 폴더 병합
    LAYER/신규(DBF/SHP, 보통 수 MB)만 웹으로 올리고, 용량이 큰 파일만 SFTP로
    미리 올려서 검수 시 이름이 같은 폴더끼리 자동 병합한다.
      1) SFTP로 아래 구조로 미리 올려둔다(폴더명은 검수 화면에 그대로 입력):
           D:\Dsmap_ROAD\server\uploads\bulk-import-incoming\<폴더명>\LAYER\통합\PHOTO\...
           D:\Dsmap_ROAD\server\uploads\bulk-import-incoming\<폴더명>\LAYER\통합\STR\...
           D:\Dsmap_ROAD\server\uploads\bulk-import-incoming\<폴더명>\ETC\TOP\...
         (LAYER/신규는 여기 올리지 않는다 — 그건 웹에서 올림)
      2) "일괄등록" 화면 "ZIP 업로드" 탭에서 아래 둘 중 하나로 작은 쪽(LAYER/신규)을
         올린다:
           - zip으로 압축해서 업로드, 또는
           - 압축 없이 "ZIP 없이 폴더째로 선택"으로 로컬 폴더를 그대로 선택
             (브라우저가 폴더 안 파일들을 개별적으로 올림, 압축 단계 자체가 생략됨)
         로컬에서 고른 폴더 이름이 1)의 <폴더명>과 같으면 "사전 업로드 폴더명"에
         자동으로 채워져 두 폴더가 자동으로 연동된다(다르면 직접 수정 가능).
         "검수 시작"을 누르면 서버가 작은 쪽(zip/폴더 업로드분)과 큰 쪽
         (bulk-import-incoming의 사전 업로드 폴더)을 합쳐서 온전한 납품 하나로
         검수한다. 사전 업로드 폴더명을 비워두면 기존처럼 zip/폴더 하나만으로
         처리된다(하위 호환).

  [방식 B] 서버 폴더에서 바로 검수 (zip 업로드 자체를 생략)
    LAYER/신규(DBF/SHP)까지 포함해 납품 폴더 전체를 SFTP로 미리 올려두면,
    웹에서는 zip을 아예 올리지 않고 폴더를 골라 바로 검수한다.
      1) SFTP로 납품 폴더 구조 그대로 통째로 올린다:
           D:\Dsmap_ROAD\server\uploads\bulk-import-incoming\<폴더명>\LAYER\신규\...
           D:\Dsmap_ROAD\server\uploads\bulk-import-incoming\<폴더명>\LAYER\통합\...
           D:\Dsmap_ROAD\server\uploads\bulk-import-incoming\<폴더명>\ETC\TOP\...
      2) "일괄등록" 화면 "서버 폴더에서 검수" 탭에서 목록에 뜬 폴더를 고른다.
           - 폴더 1개만 체크하고 "검수 시작" → 방식 A와 동일한 검수/확정
             화면(레이어별 건수, 경고, 시군구 직접 확인 후 등록).
           - 여러 개를 체크하고 "선택 항목 일괄등록", 또는 아무것도 안 고르고
             "전체 등록" → 위에서 시군구 하나만 선택하면 목록의 각 폴더를
             순서대로 자동 검수+등록(레이어별 상세 확인 화면 없이 바로 저장).
             폴더별로 성공/실패가 로그에 표시되고, 실패한 폴더가 있어도 나머지는
             계속 진행한다(전체가 한 번에 실패하지 않음).

  공통: 폴더명은 영문/숫자/한글/공백/./_/- 만 허용(경로 조작 방지). 존재하지
  않는 폴더명을 쓰면 검수 단계에서 바로 에러가 뜬다. **방식 B(서버 폴더에서
  검수)로 등록이 완료된 폴더는 서버가 자동으로 삭제한다** — 재확인이 필요하면
  등록 전에 따로 백업해둘 것. 확정하지 않고 취소하면 폴더는 그대로 남는다.
  방식 A(zip+병합)로 merge된 사전 업로드 폴더는 자동 삭제되지 않는다(zip
  자체가 주 자료이고 이 폴더는 보조 자료라 재사용 가능성이 있어서) — 이건
  디스크 용량이 쌓이면 주기적으로 수동 정리할 것.

  구현: server/lib/bulkImportStaging.js(resolveIncomingDir/mergeIncomingDir —
  방식 A, stageFromIncomingDir/listIncomingFolders/getIncomingSourceOfUpload —
  방식 B), server/routes/bulkImport.js(/preview — zip 업로드, /preview-folder-upload
  — 폴더째 업로드(webkitdirectory), 둘 다 buildPreviewPayload로 사전 업로드
  폴더 병합 공유 / /preview-from-folder, GET /incoming — 방식 B /
  /:uploadId/confirm에서 방식 B 등록 성공 시 원본 폴더 자동 삭제).

8. 서버 IP/포트가 바뀔 때 체크리스트
--------------------------------------------------------
프론트엔드는 서버 IP를 하드코딩하지 않아서(항상 /api/... 상대경로) 신경 쓸
필요 없음. 아래만 확인하면 됨.

  [코드/설정 파일 — 실제 수정]
    - server/.env(=env.production)의 VWORLD_REFERER=https://<새IP>:<새포트>/
    - deploy/web.config의 리라이트 대상(localhost:3000)은 "내부" Node 포트가
      바뀔 때만 수정 — 외부 IP/포트(11800)는 이 파일에 없음(IIS 사이트
      바인딩에서 관리)
    - .vscode/sftp.json의 host (VS Code SFTP 확장 쓸 때만, 선택)

  [서버/외부 설정 — 코드 아님, 안 하면 실제로 접속 자체가 안 됨]
    - IIS 사이트 바인딩 포트 변경 (IIS 관리자에서 직접)
    - 방화벽 인바운드 규칙을 새 포트로 다시 허용:
        New-NetFirewallRule -DisplayName "RoadLedger-<새포트>" -Direction Inbound -Protocol TCP -LocalPort <새포트> -Action Allow
      (기존 규칙이 남아있으면 정리: Remove-NetFirewallRule -DisplayName "RoadLedger-<이전포트>",
      예: 105.24.1.170:11800로 옮겨오면서 남은 이전 규칙은 "RoadLedger-8081")
    - **VWorld 개발자센터에서 키의 서비스 URL을 새 IP:포트로 재등록** — 이거
      빼먹으면 지도가 401/403으로 안 뜸(가장 놓치기 쉬운 단계, 실제로 겪은 문제)

  [문서 — 동작엔 영향 없지만 최신화 권장]
    - README.md, 이 파일(deploy/서버배포_가이드.txt) 전반에 이전 서버 주소의
      예시가 안 남아있는지 확인(현재는 105.24.1.170:11800 기준으로 갱신됨)

9. 폐쇄망(오프라인) 서버에 새로 구축할 때
--------------------------------------------------------
새 서버가 인터넷이 안 되는 폐쇄망일 수 있는 경우, npm이 필요한 두 가지
(PM2, 앱의 node_modules)를 인터넷 되는 컴퓨터에서 미리 준비해서 옮겨야 한다.

  1) PM2 오프라인 준비 (인터넷 되는 컴퓨터에서)
     npm install -g pm2 pm2-windows-startup
     Compress-Archive -Path "$env:APPDATA\npm" -DestinationPath "$env:USERPROFILE\Desktop\pm2-offline.zip"

     ⚠ 이 npm install이 PowerShell에서 아래 오류로 막히는 경우가 있음:
       "이 시스템에서 스크립트를 실행할 수 없으므로 ...npm.ps1 파일을 로드할
       수 없습니다" (PSSecurityException / UnauthorizedAccess)
     → PowerShell 실행 정책 문제. 먼저 실행:
       Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
     그 다음 npm install 명령을 다시 실행(복사-붙여넣기 시 명령 두 개가 줄바꿈
     없이 한 줄로 붙어버려서 "pm2-windows-startupnpm install..." 같은 존재하지
     않는 패키지를 찾는 404 에러가 날 수 있음 — 이땐 그냥 명령을 한 줄로
     깨끗하게 다시 입력).

  2) 앱 의존성(server/node_modules) 오프라인 준비 (같은 컴퓨터에서)
     Compress-Archive -Path "D:\DSMAP\DSMAP_1.0_도로대장시스템\road-ledger-app\server\node_modules" -DestinationPath "$env:USERPROFILE\Desktop\server-node_modules.zip"
     (경로는 로컬 프로젝트 폴더 기준으로 맞출 것)

  3) 새 서버로 이동
     인터넷이 없으니 SFTP도 안 됨 — USB 등 이동식 매체로 옮길 것.
     - pm2-offline.zip → 새 서버의 %APPDATA%\npm 에 풀기:
         Expand-Archive -Path "pm2-offline.zip" -DestinationPath "$env:APPDATA\npm" -Force
       새 PowerShell 창에서 pm2 -v로 정상 인식되는지 확인.
     - server-node_modules.zip → 앱 코드(D:\Dsmap_ROAD\server\)에 올린 뒤
       node_modules 폴더로 풀기. 이렇게 하면 서버에서 npm install 자체를
       생략할 수 있다(3-3단계 건너뜀).

  참고: 이 모든 npm 오프라인 문제 자체가 부담스러우면, PM2 대신 단일
  실행파일인 NSSM으로 Windows 서비스 등록하는 방법도 있다(별도 안내 가능,
  다만 현재 운영 서버(105.24.1.170)는 PM2 기준으로 문서/ecosystem.config.js가
  맞춰져 있어 서버마다 방식이 달라지는 점은 감안할 것).

10. HTTPS로 구성할 때
--------------------------------------------------------
지금까지의 105.24.1.170 서버는 HTTP(11800)만 쓰지만, 새 서버를 HTTPS로
구성하려면 아래를 따른다.

  ⚠ 기존에 준비해둔 DSMap-cert.cer(Subject/Issuer가 컴퓨터 이름 WIN-XXXX
  형태인 자체서명 인증서)은 환경(서버/IP/호스트명)이 바뀌면 대부분 못 쓴다.
  자체서명 인증서는 개인키가 "발급한 그 컴퓨터"의 인증서 저장소에만 있어서,
  다른 서버로 옮기면 개인키가 없어 바인딩이 안 되거나(가장 흔한 경우),
  개인키가 있어도 Subject(CN)가 실제 접속 주소(새 IP/도메인)와 달라 브라우저가
  "이름 불일치" 경고를 계속 띄운다. → **새 서버에서 그 서버 기준으로 새로
  발급하는 게 정석.** 기존 .cer은 폐기하거나 참고용으로만 남겨둘 것.

  1) 새 서버에서 새 인증서 발급 (관리자 PowerShell, IIS 설치 후 아무 때나)
     New-SelfSignedCertificate -DnsName "<새IP>", "<새호스트명>" -CertStoreLocation "cert:\LocalMachine\My" -FriendlyName "DSMap Road Ledger" -NotAfter (Get-Date).AddYears(5)

     -DnsName에는 실제 접속에 쓸 값을 전부 나열(IP와 호스트명 둘 다 접속할
     가능성이 있으면 둘 다, 콤마로 구분 — SAN(주체 대체 이름)으로 들어가서
     어느 쪽으로 접속해도 이름 불일치가 안 남). 기본 유효기간(1년)은 내부망
     인증서치고 짧아 자주 갱신해야 하니 -NotAfter로 5년 정도로 넉넉히 잡음
     (그만큼 보안상 장기 신뢰이므로, 외부 공개망이면 짧게 잡는 게 정석이지만
     내부 폐쇄망 서버라 실용성 우선).

     발급 확인:
       Get-ChildItem Cert:\LocalMachine\My | Where-Object { $_.FriendlyName -eq "DSMap Road Ledger" } | Format-List Subject, NotAfter, Thumbprint

  2) (선택) 클라이언트 PC 배포용으로 .cer로 내보내기
     $cert = Get-ChildItem Cert:\LocalMachine\My | Where-Object { $_.FriendlyName -eq "DSMap Road Ledger" }
     Export-Certificate -Cert $cert -FilePath "D:\DSMap-cert-new.cer"

  3) IIS 사이트에 HTTPS 바인딩 추가 (IIS 관리자, 최초 1회)
     사이트 선택 → 우측 "바인딩(Bindings)..." → 추가 → 유형: https, 포트
     선택(예: 443 또는 8444 등 원하는 포트), SSL 인증서 드롭다운에서 방금
     만든 "DSMap Road Ledger" 선택 → 확인.
     (내부적으로 Node에 넘기는 web.config의 리라이트 대상(http://localhost:3000)
     은 그대로 둔다 — TLS 종료는 IIS가 하고 내부 전달은 계속 평문 HTTP라
     web.config 자체는 HTTP/HTTPS 여부와 무관하게 안 바뀜.)

  4) 방화벽 인바운드 허용 (새 HTTPS 포트로)
     New-NetFirewallRule -DisplayName "RoadLedger-HTTPS-<포트>" -Direction Inbound -Protocol TCP -LocalPort <포트> -Action Allow

  5) server/.env(=env.production) 수정
     VWORLD_REFERER=https://<실제IP또는도메인>:<포트>/

  6) VWorld 개발자센터에서 키의 서비스 URL을 위 5)와 정확히 같은 값(https,
     포트 포함)으로 재등록 — 8단계 체크리스트와 동일한 이유로 빼먹으면
     지도가 401/403.

  7) (선택) 클라이언트 PC에서 "안전하지 않음" 경고 없애기
     자체서명 인증서는 브라우저가 기본적으로 신뢰하지 않는다. 2)에서 내보낸
     .cer을 접속하는 각 PC에 배포해 신뢰 저장소에 넣으면 경고가 사라진다:
       Import-Certificate -FilePath "DSMap-cert-new.cer" -CertStoreLocation Cert:\LocalMachine\Root
     (관리자 PowerShell 필요. 안 해도 접속 자체는 되고, 브라우저에서
     "고급 → 계속 진행" 클릭 한 번으로 우회 가능 — 필수는 아님.)

  [참고] 기존 .cer을 그대로 확인만 해보고 싶다면(재사용 가능한지 판단용):
     $cert = New-Object System.Security.Cryptography.X509Certificates.X509Certificate2("경로\DSMap-cert.cer")
     $cert | Format-List Subject, Issuer, NotBefore, NotAfter, Thumbprint

11. Windows/PowerShell 작업 시 자주 겪는 문제 모음
--------------------------------------------------------
2026-08-31, 두 번째 서버(110.24.1.116, 행정망/폐쇄망, 경로는 D:\App\
road-ledger-app)를 실제로 구축하면서 겪은 것들. 서버가 달라도 반복될 만한
일반적인 Windows/PowerShell/Node/PostgreSQL/PM2 문제라서 따로 모아둔다.
아래는 전부 그 서버의 실제 경로(D:\App\...) 기준 — 다른 서버에 적용할 땐
경로만 그 서버 기준으로 바꿀 것.

  [A] npm install이 PowerShell 실행 정책 때문에 막힘
      "이 시스템에서 스크립트를 실행할 수 없으므로 ...npm.ps1 파일을 로드할
      수 없습니다" (PSSecurityException / UnauthorizedAccess)
      → 아래 실행 후 재시도:
        Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

  [B] node/npm 설치는 됐는데 CommandNotFoundException — 원인이 여러 개라
      순서대로 확인:
      1) 설치 파일(msi)을 실제로 더블클릭해서 설치 마법사를 끝까지
         진행했는지 확인. 파일이 폴더에 있는 것과 설치된 건 다르다.
         확인: Get-ChildItem "C:\Program Files\nodejs\node.exe"
      2) 설치 직후라면 "새 창"이 아니라 "기존 창"에서 테스트 중일 수 있음 —
         PowerShell 창을 완전히 닫고 새로 열어서 재시도.
      3) 그래도 안 되면 PATH가 실제로 등록됐는지 확인:
         [Environment]::GetEnvironmentVariable("Path","Machine") -split ';' | Select-String nodejs
         안 나오면 수동 등록(관리자 권한 필요):
         [Environment]::SetEnvironmentVariable("Path", [Environment]::GetEnvironmentVariable("Path","Machine") + ";C:\Program Files\nodejs\", "Machine")
      4) 등록까지 확인했는데도 새 창에서 안 되면 — Windows 탐색기(Explorer)가
         로그인 시점의 PATH를 캐시해두고 있어서, 시작 메뉴로 여는 새 창도
         그 예전 값을 물려받는 경우가 있다(자주 겪음). 해결:
           Stop-Process -Name explorer -Force
         (화면이 깜빡이고 다시 뜬다) 그래도 안 되면 컴퓨터를 재부팅하는 게
         가장 확실하다.
      5) 지금 당장 급하면 PATH 문제를 아예 무시하고 전체 경로 + 세션 한정
         PATH 추가로 진행 가능:
           $env:Path += ";C:\Program Files\nodejs\"
           & "C:\Program Files\nodejs\node.exe" -v
           & "C:\Program Files\nodejs\npm.cmd" install --omit=dev

  [C] PowerShell 명령 작성 시 자주 하는 실수
      - cd 폴더 & "실행파일" 인자   ← 틀림. PowerShell의 &는 "이 문자열을
        명령으로 실행해라"는 뜻이지 명령 연결 연산자가 아니다. cd와 실행은
        반드시 줄을 나눠서:
          cd D:\App\road-ledger-app\server
          & "C:\Program Files\nodejs\npm.cmd" install --omit=dev
      - "전체경로\파일.exe" 인자   ← 틀림(맨 앞에 & 빠짐). 따옴표로 감싼
        경로를 실행하려면 반드시 맨 앞에 & 필요.
      - node.exe를 node.eve로 오타내는 등 — 전체경로 직접 타이핑할 때
        Get-ChildItem 등으로 확인된 실제 경로를 그대로 복붙하는 게 안전.

  [D] PostgreSQL 관련
      - psql이 PATH에 없음 → 전체경로로 실행(버전 번호는 실제 설치 버전):
          & "C:\Program Files\PostgreSQL\18\bin\psql.exe" ...
      - 한글 깨짐(인코딩 UHC) → 매번 이거 먼저 실행:
          Set-Item Env:PGCLIENTENCODING "UTF8"
        ($env:PGCLIENTENCODING = "UTF8" 형태가 이 서버에서는 원인 불명으로
        CommandNotFoundException을 낸 적이 있음 — Set-Item 방식이 더 안전)
      - CREATE USER/DATABASE를 따옴표 없이 만들면(예: CREATE DATABASE
        DSMap;) PostgreSQL이 자동으로 소문자로 바꿔서 저장한다(dsmap으로).
        나중에 -d DSMap(대문자 섞어서)으로 접속하면 "데이터베이스 없음"
        에러가 난다 — 실제로 겪음. 두 가지 해결책:
          (a) 대소문자를 유지하고 싶으면 만들 때부터 큰따옴표로 감싼다:
              CREATE USER "DSMap" WITH PASSWORD '비번';
              CREATE DATABASE "DSMap" OWNER "DSMap";
              이후 모든 명령(-U, -d, .env의 PGUSER/PGDATABASE)도 항상
              정확히 "DSMap" 대소문자로 통일해야 한다.
          (b) 훨씬 간단한 대안: 처음부터 전부 소문자(dsmap)로 통일. 이후
              헷갈릴 일이 없다.
      - psql -c "..." 안에 큰따옴표를 또 넣어야 할 때(위 (a)처럼) PowerShell
        이스케이프가 꼬여서 명령 자체가 깨지는 경우가 있었다(인자가 어디서
        끊기는지 PowerShell이 잘못 판단해서 뒷부분이 전부 별개 인자로
        분리되며 에러). 이럴 땐 -c 대신 SQL을 파일로 만들어서 -f로 실행하는
        게 훨씬 안전하다:
          Remove-Item D:\App\setup.sql -ErrorAction SilentlyContinue
          Add-Content -Path D:\App\setup.sql -Value 'CREATE USER "DSMap" WITH PASSWORD ''비번'';' -Encoding ASCII
          Add-Content -Path D:\App\setup.sql -Value 'CREATE DATABASE "DSMap" OWNER "DSMap";' -Encoding ASCII
          Get-Content D:\App\setup.sql   ← 두 줄로 깔끔하게 나오는지 먼저 확인
          & "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -f D:\App\setup.sql
        (@'...'@ 형태의 여러 줄 here-string으로 한 번에 쓰려다가 줄바꿈이
        깨져서 두 문장이 한 줄에 붙어버린 적이 있음 — Add-Content로 한 줄씩
        추가하는 방식이 훨씬 안정적이었다.)
      - 스키마(schema.sql, gov_facility_schema.sql) 적용을 깜빡하고
        seed-admin.js부터 실행하면 "accounts 이름의 릴레이션이 없습니다"
        에러가 난다 — 반드시 순서대로: CREATE USER/DATABASE → GRANT →
        schema.sql → gov_facility_schema.sql → seed-admin.js.

  [E] PM2 오프라인 설치(zip) 압축 풀 때 폴더가 한 겹 더 생기는 문제
      Compress-Archive -Path "$env:APPDATA\npm" ... 로 만든 zip은 "npm"
      폴더 자체가 zip 안에 들어있어서, 압축을 풀 때 목적지를
      "$env:APPDATA\npm"으로 지정하면 실제로는 그 안에 npm 폴더가 하나 더
      생겨서 "...\npm\npm\pm2.cmd"가 된다(실제로 겪음). 압축 풀고 나면
      바로 실제 위치부터 확인할 것:
        Get-ChildItem "$env:APPDATA\npm" -Filter pm2.cmd -Recurse
      나온 경로를 그대로 써서 이후 명령 진행(예: "...\npm\npm\pm2.cmd").

  [F] pm2.cmd 실행 시 "'node'은(는) 내부 또는 외부 명령... 아닙니다"
      pm2.cmd 배치 스크립트 내부에서 자체적으로 PATH에서 node를 찾기 때문에,
      이 세션에 PATH가 안 잡혀있으면 pm2 자체는 실행돼도 내부에서 실패한다.
      해결(이 세션에서 임시로 PATH 추가):
        $env:Path += ";C:\Program Files\nodejs\"
        & "$env:APPDATA\npm\npm\pm2.cmd" -v

  [G] IIS가 502.3을 반환하는데 당황할 필요 없는 경우
      Node/PM2 앱을 아직 안 띄운 상태에서 사이트에 접속하면 IIS(ARR)가
      "뒤에 아무도 응답 안 함" 의미로 502.3을 반환한다 — IIS/web.config
      자체는 정상이라는 신호(요청을 제대로 받아서 넘기려고 시도했다는 뜻).
      npm install → 스키마 적용 → seed-admin.js → PM2 start까지 다 끝내면
      저절로 사라진다.
     Subject가 새 서버의 실제 접속 주소와 다르면(대부분 다를 것) 위 1)로 새로
     발급할 것.


--------------------------------------------------------
12. PM2 → NSSM 전환 가이드 (선택 — 아직 실제 적용 전, 준비만)
--------------------------------------------------------
왜 바꾸나: 두 번째 서버(폐쇄망) 구축 때 겪은 문제 대부분(npm install 실행정책,
node/npm PATH 미등록, pm2.cmd 내부에서 node를 못 찾음, npm 글로벌 폴더 오프라인
zip이 이중폴더로 풀림 — 위 9번/11번 섹션)은 IIS 리버스프록시 구조 자체가 아니라
"PM2가 npm/Node.js 설치와 PATH에 의존하는 방식"이 원인이었다. NSSM은 npm과
무관한 단일 실행파일(exe 하나, 수백 KB)이라 이 의존성이 통째로 사라진다.
IIS(리버스프록시)·PostgreSQL·web.config는 전혀 안 바뀐다 — 오직 "Node 프로세스를
누가 띄우고 감시하느냐"만 PM2에서 NSSM으로 바뀌는 것.

  0) NSSM 준비 (인터넷 되는 컴퓨터에서, 폐쇄망 서버면 USB로 옮길 것)
     https://nssm.cc/download 에서 최신 버전 zip 다운로드 후 압축 해제.
     64비트 서버면 win64\nssm.exe 하나만 있으면 된다(설치 불필요, 그냥 실행파일).
     서버의 고정 위치로 복사해둘 것(예: D:\Dsmap_ROAD\nssm\nssm.exe) — 서비스
     등록 후에도 이 exe가 계속 필요하므로 지우면 안 됨.

     ⚠ PM2 때와 달리 npm install도, PATH 등록도, "새 창 열기"도 필요 없다 —
     exe 하나 복사해서 바로 쓰는 도구라 9번/11번 섹션의 오프라인 설치 문제들이
     원천적으로 발생하지 않는다.

  1) 기존 PM2 프로세스 정리 (전환 대상 서버에서, 서비스 하나만 살아있어야
     포트 충돌이 안 남)
       pm2 stop road-ledger
       pm2 delete road-ledger
       pm2 save
     재부팅 시 PM2가 다시 아무것도 안 살리도록 자동시작 등록도 해제:
       pm2-startup uninstall
     (작업 스케줄러에서 "PM2"로 검색해 관련 작업이 남아있지 않은지 눈으로도
     확인 — 11번 섹션에서 pm2-startup install 확인할 때 쓴 방법과 동일)

  2) NSSM으로 서비스 등록 (관리자 PowerShell)
       & "D:\Dsmap_ROAD\nssm\nssm.exe" install road-ledger "C:\Program Files\nodejs\node.exe" "D:\Dsmap_ROAD\server\index.js"
       & "D:\Dsmap_ROAD\nssm\nssm.exe" set road-ledger AppDirectory "D:\Dsmap_ROAD\server"
       & "D:\Dsmap_ROAD\nssm\nssm.exe" set road-ledger Start SERVICE_AUTO_START

     node.exe 전체경로가 이 서버에서 다르면 먼저 확인:
       Get-ChildItem "C:\Program Files\nodejs\node.exe"

     ⚠ AppDirectory(작업 디렉터리)를 server 폴더로 지정하는 게 핵심 — 앱이
     .env를 상대경로로 읽기 때문에(지금 pm2도 ecosystem.config.js의 cwd로
     같은 역할을 함), 이걸 빠뜨리면 .env를 못 찾아 DB 접속정보 등이 비어서
     바로 죽는다.

  3) 로그 파일 지정 (선택이지만 강력 권장 — pm2 logs 대신 쓸 것)
       New-Item -ItemType Directory -Path "D:\Dsmap_ROAD\server\logs" -Force
       & "D:\Dsmap_ROAD\nssm\nssm.exe" set road-ledger AppStdout "D:\Dsmap_ROAD\server\logs\out.log"
       & "D:\Dsmap_ROAD\nssm\nssm.exe" set road-ledger AppStderr "D:\Dsmap_ROAD\server\logs\error.log"
       & "D:\Dsmap_ROAD\nssm\nssm.exe" set road-ledger AppRotateFiles 1
       & "D:\Dsmap_ROAD\nssm\nssm.exe" set road-ledger AppRotateBytes 10485760

     (로그가 10MB 넘으면 자동으로 회전 — 안 해두면 로그 파일이 무한정 커진다)

  4) 서비스 시작 + 확인
       & "D:\Dsmap_ROAD\nssm\nssm.exe" start road-ledger
       Get-Service road-ledger
       Get-Content "D:\Dsmap_ROAD\server\logs\out.log" -Tail 20

     STATUS가 Running이고 out.log에 서버 정상 기동 로그(포트 리스닝 메시지 등)가
     보이면 성공. 브라우저에서 접속 테스트(3-6 참고)까지 확인.

     ⚠ 실패해서 바로 롤백해야 하면:
       & "D:\Dsmap_ROAD\nssm\nssm.exe" stop road-ledger
       & "D:\Dsmap_ROAD\nssm\nssm.exe" remove road-ledger confirm
       cd D:\Dsmap_ROAD\server
       pm2 start ecosystem.config.js
       pm2 save
     (포트 3000을 NSSM/PM2 중 하나만 점유할 수 있으므로, 문제가 생기면 먼저
     nssm stop으로 완전히 내린 뒤 pm2로 되돌릴 것 — 둘 다 떠있으면 둘 중
     하나는 포트 충돌로 못 뜬다)

  5) 재부팅 후 자동시작 확인 (최초 적용 시 한 번은 꼭 검증)
     서버 재부팅 → 로그인 없이도(서비스는 로그인 전에도 동작) 몇 분 뒤
     브라우저로 접속 테스트. 안 되면:
       Get-Service road-ledger   ← Stopped면 수동 시작 후 원인 확인
       & "D:\Dsmap_ROAD\nssm\nssm.exe" edit road-ledger   ← GUI로 설정 확인(경로 오타 등)

  6) 이후 운영 명령 대응표 (PM2 → NSSM)
       pm2 restart road-ledger        → Restart-Service road-ledger
       pm2 stop road-ledger           → Stop-Service road-ledger
       pm2 logs road-ledger --lines 50 → Get-Content "D:\Dsmap_ROAD\server\logs\out.log" -Tail 50
       pm2 list                       → Get-Service road-ledger  (또는 nssm status road-ledger)
     6번 섹션(재배포 절차)의 "pm2 restart road-ledger"도 전환 후에는
     "Restart-Service road-ledger"로 바꿔서 진행할 것.

  7) 크래시 시 자동 재시작 — 기본값 그대로 둘 것
     NSSM은 등록만 하면 기본적으로 프로세스가 비정상 종료될 때 자동
     재시작한다(PM2와 동일한 안전장치). 별도 설정 불필요. 재시작이
     너무 잦으면(무한 크래시 루프) 원인은 로그(3)의 error.log)로 확인하고,
     재시작 간격을 늘리고 싶을 때만:
       & "D:\Dsmap_ROAD\nssm\nssm.exe" set road-ledger AppThrottle 1500

  적용 대상: 지금 이 문서 기준 대상 서버(105.24.1.170)는 아직 PM2 그대로
  운영 중 — 이 섹션은 다음에 실제로 전환하기로 결정했을 때 그대로 따라 하면
  되는 준비된 절차. 두 번째 서버(110.24.1.116, 폐쇄망)처럼 오프라인 설치
  자체가 부담인 환경에 새로 구축할 때는 처음부터 PM2 대신 이 방식으로
  구축하는 것도 고려할 것(9번 섹션 참고).

13. 로그 관리 (접속 이력 / 서버 로그 / 보관 규칙)
--------------------------------------------------------
추가일: 2026-10-21. 로그는 목적이 다른 두 곳에 따로 남는다.

  [A] 접속·변경 이력 — DB(audit_log 테이블), 화면: 관리자 모드 → "변경이력" 탭
      - 데이터 변경: 구간 등록/수정/삭제, 일괄등록
      - 접속·계정: 로그인 성공/실패/잠금, 로그아웃, 회원가입 신청·승인,
        계정 생성·삭제 (누가/언제/어느 IP에서). 비밀번호는 절대 기록하지 않는다.
      - 화면 상단 필터로 "로그인 실패"만 모아 볼 수 있다(무차별 대입 확인용).
      - ⚠ 기존 서버는 배포 시 schema.sql을 다시 적용해야 한다(audit_log.ip 컬럼,
        accounts.status 컬럼 추가 — 둘 다 IF NOT EXISTS라 재실행해도 안전).
      - 이 이력은 자동 삭제하지 않는다. 보관기간은 기관 지침을 따를 것(접속기록은
        보통 최소 1년, 개인정보를 다루면 2년 이상 요구). 오래된 행을 정리해야
        하면 관리자가 DB에서 보관기간 지난 행만 직접 지운다(예: created_at 기준).

  [B] 서버 운영 로그 — 파일: <앱 폴더>\server\logs\app-YYYY-MM-DD.log
      - 에러, 느린 요청(5초 이상), 4xx/5xx API 응답이 날짜별 파일로 쌓인다.
        (로그인 실패 401은 [A]에 따로 남으므로 여기선 제외)
      - 앱이 직접 날짜별로 나누고, LOG_RETENTION_DAYS(.env, 기본 365일)보다 오래된
        파일은 자동 삭제한다 → PM2든 NSSM이든, pm2-logrotate 같은 모듈을 못
        까는 폐쇄망에서도 별도 설정 없이 동작한다. 보관기간을 바꾸려면
        .env에 LOG_RETENTION_DAYS=730 처럼 적고 재시작.
      - PM2/NSSM이 따로 쌓는 out.log/error.log(시작·종료 메시지, 크래시 직전
        출력)는 앱이 못 나누므로 아래처럼 로테이션을 걸어둔다.
          PM2  : pm2 install pm2-logrotate  (인터넷 되는 서버만. 폐쇄망이면 12번의
                 NSSM 방식 사용)
                 pm2 set pm2-logrotate:max_size 10M
                 pm2 set pm2-logrotate:retain 30
          NSSM : 12번 섹션 3)의 AppRotateFiles / AppRotateBytes(10MB) 설정 그대로

  [C] 접속자 IP가 전부 127.0.0.1로 찍힐 때 (IIS 리버스프록시 환경)
      앱은 IIS와 같은 서버에서 붙으므로 loopback의 X-Forwarded-For만 신뢰하도록
      설정돼 있다(server/index.js의 trust proxy). 단, IIS가 그 헤더를 실어줘야 한다:
        IIS 관리자 → 서버 최상위 노드 → "Application Request Routing Cache" →
        우측 "Server Proxy Settings..." → "Preserve client IP in the following HTTP
        header" 체크 + 헤더 이름 X-Forwarded-For → Apply
      (web.config에서 서버 변수로 넣는 방식은 이 서버처럼 구성 섹션이 잠겨 있으면
       500.19로 죽을 수 있어 쓰지 않는다 — 위 4번 트러블슈팅 참고)
      이 설정을 안 해도 동작은 정상이고 IP만 127.0.0.1로 남는다.

  [D] 로그인 잠금
      같은 아이디로 5회 연속 실패하면 10분간 로그인을 막는다(없는 아이디도 똑같이
      세서 아이디 존재 여부를 알 수 없게 함). 서버를 재시작하면 잠금이 풀린다.
      잠금/횟수는 server/routes/auth.js의 MAX_LOGIN_FAILS / LOCK_MINUTES.

  [E] 로그 파일 접근 권한 (현업에서 중요)
      로그는 앱 관리자도 함부로 지우지 못해야 의미가 있다. server\logs 폴더는
      IIS_IUSRS/일반 사용자에겐 권한을 주지 않고, 서비스 실행 계정과 서버
      관리자만 접근하게 NTFS 권한을 제한할 것.

14. 보안 설정 (HTTPS / 쿠키 / 비밀번호 / 세션)
--------------------------------------------------------
추가일: 2026-10-21.

  [A] HTTPS — 보안감사에서 가장 먼저 지적되는 항목
      현재 운영 주소가 http://(암호화 없음)이면 로그인 비밀번호가 평문으로 오간다.
      10번 섹션(HTTPS로 구성할 때)의 인증서 발급 + IIS 바인딩을 마친 뒤, 아래를 켠다:
        server\.env 에  COOKIE_SECURE=true  추가 후 서비스 재시작
      켜면 (1) 로그인 쿠키에 Secure 속성이 붙고 (2) HSTS 헤더가 나간다.
      ⚠ HTTP로 서비스 중에 켜면 쿠키가 안 먹어 로그인이 안 된다 — 반드시 HTTPS 접속이
        확인된 뒤에만. 문제가 생기면 COOKIE_SECURE 줄을 지우고 재시작하면 원복된다.
      (Node는 localhost에서만 접근되고 TLS는 IIS가 끝낸다는 전제 — 3000 포트 외부 개방 금지)

  [B] 세션 비밀키(SESSION_SECRET)
      운영(NODE_ENV=production)에서 SESSION_SECRET이 없거나 기본값/"<...>" 그대로면
      서버가 기동을 거부한다(공개된 기본 키로 세션 쿠키가 위조되는 것 방지). 16자 이상 무작위 값을
      넣을 것(예: PowerShell  [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')).

  [C] 비밀번호 정책 / 변경 / 재설정
      - 아이디 영문·숫자·._- 4~30자, 비밀번호 8자 이상(아이디와 같으면 불가) —
        관리자 계정 생성, 회원가입, 비밀번호 변경/재설정 모두 같은 규칙.
      - 본인 변경: 상단바의 열쇠 아이콘 → 현재 비밀번호 확인 후 변경. 변경하면 그 계정의
        다른 기기 로그인은 모두 해제된다. 현재 비밀번호를 5번 틀리면 로그인 잠금과 같은
        규칙(10분)으로 잠긴다.
      - 분실 시: 관리 콘솔 → 회원·계정 관리 → 그 계정의 열쇠 아이콘 → 임시 비밀번호 지정. 그 계정은
        임시 비밀번호로 로그인하면 새 비밀번호로 바꾸기 전까지 아무 기능도 못 쓴다.

15. 운영 서버 백업 / 복구
--------------------------------------------------------
추가일: 2026-10-21. 로컬 PC용(Docker DB)은 프로젝트 루트의 backup-db.bat, 운영 서버(PostgreSQL을
Windows에 직접 설치)용은 deploy\backup-prod.ps1 이다(deploy 폴더 그대로 서버에 올려도 됨).

  1) 백업이 하는 일 (실행 1회 = 날짜별 폴더 1개)
       road_ledger.dump  : pg_dump -Fc (DB 전체) + pg_restore -l 로 덤프가 읽히는지 바로 검증
       uploads\          : server\uploads 복사(일괄등록 임시/SFTP 사전업로드 폴더는 제외)
       backup.log        : 단계별 결과 기록. 실패하면 종료코드 1
       KeepDays(기본 30일)가 지난 날짜 폴더는 자동 삭제

  2) 수동 실행(처음엔 반드시 한 번 직접 돌려서 확인)
       powershell -NoProfile -ExecutionPolicy Bypass -File D:\Dsmap_ROAD\deploy\backup-prod.ps1 -AppDir D:\Dsmap_ROAD -BackupRoot E:\Backup\road-ledger
     - -BackupRoot는 앱이 설치된 디스크와 "다른" 드라이브(또는 네트워크 공유)로 잡을 것 —
       같은 디스크면 디스크가 죽을 때 백업도 같이 사라진다.
     - psql과 마찬가지로 pg_dump.exe 경로의 버전 번호(-PgBin, 기본 ...\PostgreSQL\18\bin)는
       서버에 설치된 실제 버전으로 맞출 것.
     - ⚠ 이 스크립트는 문법 검사만 마쳤고 실제 운영 PostgreSQL에 대해선 아직 실행해보지 않았다
       (개발 PC엔 Windows용 pg_dump가 없음) — 서버에서 첫 실행 결과(backup.log)를 꼭 확인할 것.

  3) 매일 자동 실행 (작업 스케줄러, 관리자 PowerShell)
       $a = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument '-NoProfile -ExecutionPolicy Bypass -File "D:\Dsmap_ROAD\deploy\backup-prod.ps1" -AppDir "D:\Dsmap_ROAD" -BackupRoot "E:\Backup\road-ledger"'
       $t = New-ScheduledTaskTrigger -Daily -At 02:00
       Register-ScheduledTask -TaskName 'RoadLedger-Backup' -Action $a -Trigger $t -User 'SYSTEM' -RunLevel Highest
     등록 후 작업 스케줄러에서 "마지막 실행 결과"가 0x0 인지 주기적으로 확인.

  4) 복구 연습 — 백업은 "복구해봐야" 백업이다. 분기에 한 번은 테스트용 DB에 복원해서 확인할 것:
       & "C:\Program Files\PostgreSQL\18\bin\pg_restore.exe" -h localhost -p <포트> -U <계정> -d <테스트DB> --clean --if-exists <백업폴더>\road_ledger.dump
       robocopy <백업폴더>\uploads <복구할 앱폴더>\server\uploads /MIR
     (운영 DB에 바로 --clean 복원하면 현재 데이터가 지워지니, 대상 DB 이름을 반드시 두 번 확인)

  5) 접속 이력(audit_log)도 DB 안에 있으므로 이 백업에 같이 들어간다. 보관기간(최소 1년 이상,
     기관 지침) 이상으로 백업을 보관해야 이력 증빙이 유지된다 — KeepDays를 그에 맞춰 늘리거나
     월 1회분을 별도 보관할 것.

16. 대용량 내려받기(전체자료 ZIP) — 스트리밍 방식
--------------------------------------------------------
추가일: 2026-10-23. "전체자료 내려받기"(노선/구간의 SHP·DBF·사진·보고서·도면 ZIP)는 서버 메모리에 ZIP을 통째로
만들지 않고, 파일을 하나씩 읽어 압축하면서 바로 보낸다(archiver). 노선 여러 개·수 GB도 서버 메모리는 거의
늘지 않고, ZIP 4GB/65,535개 한계도 없다(필요할 때만 ZIP64로 자동 전환).
  - 개발 PC 시험: 5.1GB(1.2GB 파일 4개) 내려받기 → 서버 메모리 116MB → 최대 145MB, ZIP CRC 검사 통과.
  - 브라우저는 파일 전체를 메모리에 받지 않고 일반 다운로드로 디스크에 바로 저장한다.
  - 받는 도중 연결이 끊기면 처음부터 다시 받아야 한다(이어받기 없음). 한 번에 수십 GB가 필요하면 노선을 나눠 받을 것.
  - 내려받기마다 "자료 내려받기" 이력이 남는다(접속·변경 이력 화면에서 종류로 거를 수 있음).

IIS(ARR) 설정 확인 — ⚠ 운영 서버에서 아직 시험하지 못했다(개발 PC엔 IIS가 없음). 큰 파일이 중간에 끊기거나
502/504가 나면 아래를 확인:
  1) IIS 관리자 > 서버 이름 선택 > "Application Request Routing Cache" > 우측 "Server Proxy Settings"
       Time-out(초): 기본값(30초)보다 크게. 내려받기는 첫 데이터가 나오기 전에 SHP/DBF를 만드는 시간이 걸린다 — 600 이상 권장.
       "Response buffer threshold"가 있으면 0으로(응답을 모아 두지 않고 바로 넘기게. 기본값이면 스트리밍 이점이 줄어든다).
  2) 응답 크기 제한은 없다(web.config의 maxAllowedContentLength는 업로드(요청) 크기만 제한한다).
  3) 서버(Node)는 이 경로의 시간 제한을 껐다(req/res.setTimeout(0)).

[일괄등록 확정(저장)도 백그라운드 작업이다 — 2026-10-23]
  - 확정을 누르면 서버가 바로 응답하고(202) 노선(납품 폴더)을 하나씩 따로 저장한다. 화면은 진행 상황(노선 n/N)을 조회한다.
    노선이 많아도 요청 하나가 오래 걸리지 않아 IIS 프록시(ARR) 응답 대기 시간에 걸리지 않는다.
  - 노선마다 따로 저장하므로 한 노선이 실패해도 나머지는 저장되고, 실패한 노선의 사진/도면 복사본은 지워진다.
    실패가 있으면 서버 폴더(사전업로드)와 임시 작업 폴더를 남겨 두니, 원인을 해결한 뒤 같은 납품을 다시 등록하면 이어서 저장된다
    (레코드는 덮어쓰기, 같은 이름의 첨부·도면은 교체되고 옛 파일은 지워진다).
  - 일괄등록은 서버에서 한 번에 하나만 돈다(진행 중에 또 누르면 "다른 일괄등록이 진행 중입니다").
  - 서버(PM2)를 다시 시작하면 진행 중이던 작업 정보는 사라진다. 이미 저장된 노선은 그대로이고, 같은 납품을 다시 등록하면 된다.
  - 개발 PC 시험(노선 3개, 사진 1,032장): 정상 완료, 노선 하나를 일부러 실패시킨 시험에서 나머지 2개 저장·실패 노선 파일 정리·재시도 완료까지 확인.

       - 노선(구간)을 삭제하면 시설물·첨부·도면·500m 조각의 DB 행이 section_trash_rows 에 그대로 보관되고, 파일은
         uploads\_section-trash\<번호> 로 옮겨진다. 보관 기간 30일(.env 의 SECTION_TRASH_DAYS 로 변경) 안에는 "복원"으로 삭제 전 상태가 된다.
       - 기간이 지나면 서버가 자동으로 완전 삭제한다(시작할 때 + 6시간마다). 용량이 급하면 항목의 "비우기"로 즉시 지울 수 있다(복원 불가).
       - 사진이 많은 노선을 지우면 그 크기만큼 디스크를 30일 동안 더 쓴다(목록에 파일 용량이 표시됨). uploads 가 있는 디스크 여유를 확인할 것.
       - 같은 구간번호가 다시 등록돼 있으면 복원할 수 없다(새로 등록된 구간을 먼저 지워야 한다).
       - 휴지통 폴더는 uploads 아래에 있으므로 uploads 백업에 같이 들어간다.
  9) 변경·접속 이력 보관·정리 (관리 콘솔 > 변경·접속 이력 > 이력 보관·정리):
       - 지침상 이력은 최소 1년 보관. 서버가 1년(365일) 안의 이력은 지우지 못하게 막는다.
       - 1년이 지난 이력을 CSV 파일로 저장한 뒤(저장 건수가 맞는 것을 확인한 뒤에만) DB에서 지운다. 파일은 AUDIT_ARCHIVE_DIR
         (기본: BACKUP_ROOT\audit-archive)에 쌓이며 화면에서 다시 내려받을 수 있다. 이 폴더도 백업 대상에 포함시킬 것.
       - 관할이 제한된 관리자는 정리·보관 파일 다운로드를 할 수 없다(모든 시군구의 이력이 한 테이블이라 전체 권한 관리자만 가능).
       - 정리 주기는 정해져 있지 않다(자동 아님). 1년 단위로 한 번씩 하면 된다.
 10) 보안 강화:
       - 관할이 제한된 관리자: 자기 시군구 계정만 보고·만들고·승인·재설정·삭제할 수 있다. 계정을 만들 때 관할을 비우거나 다른 시군구로
         지정하는 방식의 권한 상승이 막힌다. 일괄등록도 자기 시군구로만 가능하다. (전체 권한 관리자는 이전과 같다.)
       - 비밀번호 규칙: 영문 대문자·소문자·숫자·특수문자 중 3종류 이상이면 8자 이상, 2종류면 10자 이상. 아이디를 포함하거나
         같은 문자를 4번 이상 연속해서 쓸 수 없다. 새 계정 생성·비밀번호 변경·관리자 재설정에 적용된다(이미 있는 비밀번호는 그대로 로그인된다).
       - 출처 확인(CSRF): 데이터를 바꾸는 요청의 Origin/Referer 가 서비스 주소가 아니면 거부한다. IIS(ARR)가 Host 를 localhost 로 바꿔서
         넘기는 배포에서는 진짜 주소를 알 수 없어 기본값(ALLOWED_ORIGINS 비어 있음)에서는 검사를 건너뛰고 서버 로그에 경고만 남긴다.
         ➜ 운영 서버 .env 에  ALLOWED_ORIGINS=https://<접속주소>  를 넣으면 엄격하게 검사한다(쉼표로 여러 개 가능).
           넣은 뒤 로그인·저장이 정상인지 한 번 확인할 것. 막히면 로그에 "[csrf] 차단: ... 출처=... Host=..." 가 남으니 그 출처를 추가한다.
       - CDN 스크립트·스타일(OpenLayers, proj4, hls.js, dxf-parser, turf, three.js, SheetJS, Font Awesome)에 무결성 해시(SRI)를 붙였다.
         CDN 파일이 바뀌거나 변조되면 브라우저가 불러오지 않는다. 라이브러리 버전을 올릴 때는 index.html / cad-popup.html 의 integrity 값도
         새 파일의 sha384 로 같이 바꿔야 한다(openssl dgst -sha384 -binary 파일 | openssl base64 -A).

18. 시설물 검색 / 통계 엑셀 / 데이터 점검 (DB 변경 없음 — 코드 반영 + 서버 재시작만 하면 된다)
--------------------------------------------------------
  1) 시설물 검색 (지도 화면 > 검색보기 > "시설물"): 시설물 ID(일부도 가능, 예: R2315075895…), "표지 12"·"가로등 3"처럼 종류와 번호
     (RDID 끝 4자리 일련번호), 교량명 같은 이름으로 찾는다. 결과를 누르면 지도가 그 시설물로 이동하고 속성·첨부 사진/보고서가 열린다.
     "전체" 검색에도 결과가 있을 때만 "시설물" 항목이 같이 나온다.
  2) 현황 통계 엑셀 (관리 콘솔 > 통계·점검 > 엑셀 내려받기): 시트 = 요약 / 시설물 종류별 / 노선별 시설물 / 시군구별 시설물 /
     노선별 개수표 / 제출 체크리스트. 계정의 관할 범위만 집계한다. 연장·폭원은 종류별 대표 항목(교량=교량연장·총폭원 등)을 합한 값이다.
     제출 체크리스트의 "정상" 기준: 시설물과 도면이 있고, 필수항목 빈 값이 0칸이며, 모든 구간에 지도 선이 있음.
  3) 데이터 점검 (관리 콘솔 > 통계·점검 > 점검 실행): 중복 노선 / 노선에서 벗어난 시설물(기준 거리 기본 200m) / 시설물 ID 중복·불일치.
     읽기 전용이며 서버에서 한 번에 하나만 돈다. 개발 PC(시설물 약 4천 건)에서는 0.1초. 운영 DB가 훨씬 크면 시간이 더 걸릴 수 있으나
     화면은 진행 상황만 주기적으로 물으므로 IIS(ARR) 응답 대기 시간에 걸리지 않는다. 서버(PM2)를 재시작하면 점검 결과는 사라진다.

19. 도면을 지도 위에 겹쳐 보기 (프런트만 바뀜 — build-dist 후 새로고침)
--------------------------------------------------------
  - 지도 화면에서 도면(DXF)을 연 뒤 도면 툴바의 "지도 위에 겹쳐 보기"(겹친 레이어 아이콘)를 누르면 지도에 도면이 반투명으로 얹힌다.
  - 좌표계는 자동으로 고른다: 지금 선택한 구간의 선(없으면 지도 중심)과 도면의 선형 레이어가 가장 가깝게 겹치는 좌표계
    (Korea 2000 중부/서부/동부/동해, 구 TM Bessel, UTM-K 등 11종 중). 장성 TOP080001.dxf는 EPSG:5186으로 선형이 구간 선과 2m 이내로 일치했다.
  - 어긋나 보이면 패널에서 좌표계를 바꾸거나 동서/남북 보정(m)을 넣는다. 도면이 0,0 근처의 임의 좌표이거나 단위가 m가 아니면
    맞는 좌표계를 찾지 못했다고 알려 준다(겹칠 수 없음).
  - 도면은 지도 화면이 바뀔 때마다 보이는 부분만 다시 그리므로 확대해도 선명하다. 서버 변경·DB 변경은 없다.
  - 도면 좌표의 종류(2026-10 장성·화성 도면 204개를 전수 확인):
      · 노선 전체 도면(TOP…, CON… 등): 실제 측량 좌표. 장성은 Korea 2000 중부원점(EPSG:5186).
      · 500m 구간 도면(…P/…U/…Y, 파일명이 500m 구간 번호): 측량 좌표가 아니라 "시트(도곽) 좌표"다. 구간 번호마다 가로로 500씩 옮긴 같은 크기의
        도곽 안에 도로를 회전시켜 앉혀 놓은 것이라(예: 000802100000P는 x=182944~, 000802105500P는 x=188444~, y는 같음) 어떤 좌표계로도 지도에 안 맞는다.
      · 그래서 구간 도면은 도면 안의 도로 중심선(CA-ALGN-CNTL)을 시스템에 등록된 같은 500m 구간 선(road_sectors)에 맞춰 위치·회전·배율을 구해 얹는다.
        500m 구간 파일 140개 전부에서 맞춤에 성공했고(배율 0.986~1.007, 중심선 오차 중앙값 0.5m·최대 10m) 이 화면에서 좌표계 대신 "시트 좌표 자동 맞춤"으로 표시된다.
      · 구간 선에 150m 안으로 붙는 좌표계가 없고 맞출 구간 선도 없으면 "맞지 않는다"고 알리고 억지로 얹지 않는다.
      · 구간 전체 평면도 SE…(예: SE01010100000, SE02010100000)도 시트 좌표다(좌표값이 500만·290만대). 구간 선 전체에 중심선을 맞춘다.
        좌표계가 구간 선과 6m 안으로 붙을 때만 좌표계를 쓰고, 그보다 어긋나면 중심선 맞춤을 우선한다(시트가 우연히 실제 위치 근처에 놓여
        좌표계 하나가 10~20m 이내로 비슷하게 맞는 도면이 있다: 농도 303호선 횡단 Y 일부). 화성 도면 96개: 시트 맞춤 92개(오차 중앙값 0.5m·최대 2.4m), 실제 좌표 4개.

20. 2026-10-26 전체 점검에서 고친 것 (서버 반영 시)
--------------------------------------------------------
  1) 시군구가 다른데 업무키(도로종류, 노선번호, 구간)가 같은 노선의 데이터가 섞이던 문제를 고쳤다 — 예: 장성 군도 8호선 1구간과 화성 군도 8호선 1구간.
     · 조회: 구간 선택 시 시설물 개수·500m 구간 선·시설물 위치·첨부 목록이 다른 시군구 것까지 보이던 것(화성 계정이 장성 시설물 392개의 위치를
       받을 수 있었다) → 관할이 있는 계정은 자기 관할만 본다.
     · 삭제/내려받기/조서/총괄 자동생성: 한 구간을 지우거나 내려받을 때 같은 업무키의 다른 시군구 시설물까지 같이 지우거나 담던 것 → 그 구간의 시군구 것만.
     · 관할이 없는 전체 권한 계정이 업무키가 겹치는 두 시군구를 한 화면에서 보는 경우는 화면이 시군구를 구분해 요청하지 않아 아직 섞여 보일 수 있다
       (삭제·내려받기는 구간 자체의 시군구로 처리되므로 안전).
  2) 시설물 테이블 49개에 (도로종류, 노선번호, 구간) 인덱스를 추가했다. 서버에서 반드시 한 번 실행:
       psql -h <host> -U <user> -d <db> -f server\db\gov_facility_schema.sql     (IF NOT EXISTS라 안전, 데이터가 많으면 몇 분 걸릴 수 있다)
     인덱스가 없으면 구간 선택·마우스오버·삭제·내려받기가 테이블 전체를 읽는다. 노선이 수백 개로 늘면 체감 속도가 크게 떨어진다.
  3) 서버를 PowerShell Start-Process로 띄울 때 로그 파일은 절대 경로로 지정할 것(상대 경로면 실행한 위치에 쌓인다).

22. 도면·시설물 파일 올리기는 편집 모드(관리자)에서만 (2026-10-26)
--------------------------------------------------------
  - 도면 올리기(도면 뷰어의 파일 선택/업로드, 도면 자동 인식, ZIP 일괄)는 편집 모드(상단 방패 아이콘)를 켠 관리자만 보이고 가능하다.
    화면에서 숨기는 것과 별개로 서버(POST /api/routes/files, /auto, /bulk-zip)도 관리자만 받는다 — 일반 계정이 API를 직접 불러도 403.
  - 올린 도면은 서버 디스크 uploads/routes/<도로종류>__<노선번호>__<노선명>/<시각>_<파일명> 에 저장되고 route_files에 한 줄이 생긴다
    (DWG는 미리보기용 DXF도 같이 변환해 둔다). 백업 대상(uploads)에 포함된다.
  - 시설물 사진·보고서 올리기: 속성정보 창 상단의 "파일 올리기"(편집 모드에서만 보임). POST /api/sections/facility-files(관리자 전용).
    uploads/gov-facility-files/<시군구>/<시설물 테이블>/ 에 저장되고 gov_facility_files에 기록돼 일괄등록으로 붙은 파일과 똑같이 보인다.
    허용 형식: 사진 jpg·jpeg·png·gif·bmp·webp / 보고서 pdf·hwp·hwpx·doc·docx·xls·xlsx, 파일당 200MB·한 번에 20개.
    같은 시설물에 같은 이름이 있으면 덮어쓸지 먼저 묻는다. 관할 밖 시설물에는 올릴 수 없다. 올리면 변경 이력에 남는다.

  - 시설물 파일 삭제(편집 모드, 관리자 전용 DELETE /api/sections/facility-files/:id): 갤러리의 파일별 휴지통 버튼, 파일 하나를 열어 둔 속성정보 바의
    "이 파일 삭제", 사이드바 부속시설 첨부파일 목록의 줄별 버튼. DB 기록은 바로 지우고 파일은 uploads/_deleted-facility-files/ 로 옮겨 30일 뒤
    서버가 자동으로 지운다(6시간마다 점검). 그 안에는 서버에서 파일을 원래 위치로 되돌리고 gov_facility_files에 한 줄을 다시 넣어 복구할 수 있다
    (변경 이력의 "시설물 파일 삭제" 상세에 보관 경로가 남는다). 이 폴더도 uploads 백업에 들어간다.

    …-tmp(업로드 중 잠깐), bulk-import*(검수 작업 폴더·납품 폴더), _thumbs(사진 썸네일 캐시, 파일 번호로 저장),
    _section-trash/_import-trash(노선 삭제 휴지통·일괄등록 되돌리기 보관, 번호로 저장, 30일 안에 정리됨)
  [왜 분류했나] 시군구별 용량 확인·백업·정리가 쉽고, 같은 이름의 노선(예: 장성·화성 군도 8호선)이 한 폴더에 섞이지 않는다.
    파일의 실제 위치는 DB(stored_path)가 기억하므로 폴더 배치를 바꿔도 열기·다운로드는 그대로 된다.

  [운영 서버에 적용하는 순서 — 기존 파일을 새 구조로 옮긴다]
    1) 코드 반영(npm ci, build-dist) 후 서버(PM2)를 잠시 멈춘다. 반드시 먼저 DB와 uploads를 백업한다(deploy\backup-prod.ps1).
    2) 미리보기(아무것도 바꾸지 않음):   node server\db\migrate-upload-folders.js
       → 옮길 파일 수, DB 경로 갱신 건수, 건너뛰는 항목(파일이 없는 옛 기록)이 나온다.
    3) 실제 적용:                        node server\db\migrate-upload-folders.js --apply
       → 파일을 옮기고 DB 경로(도면·사용자도로관리·필지·시설물 파일, 일괄등록 되돌리기·노선 삭제 휴지통 기록 속 경로)를 같이 바꾼다.
         시군구 표시가 비어 있던 도면은 그 구간의 시군구로 채운다. 되돌릴 기록: uploads\_migration-<시각>.json
    4) 문제가 있으면:                    node server\db\migrate-upload-folders.js --rollback uploads\_migration-<시각>.json
    5) 서버를 다시 시작한다. 여러 번 실행해도 안전하다(이미 옮긴 것은 건너뜀). 업로드 폴더가 .env의 UPLOAD_DIR와 다르게 기록된 경로는 건너뛴다.
  [개발 PC 결과] 도면 273건 중 파일이 있는 259건·311개 파일(변환 DXF 포함)을 routes\12840\, routes\41590\ 로 옮겼고, 시군구 표시가 비어 있던
    도면 52건을 채웠다. 파일이 원래부터 없던 14건은 기록만 남아 있어 그대로 두었다. DB에 기록이 없는 옛 도면 파일 54개(57MB)는
    routes\군도__0008__월산-와우\ 에 남아 있다(어느 노선 것인지 기록이 없어 지우지 않았다).

25. 지도 표시 방식 변경(좌측 도로대장 트리)
  - 구간을 선택해도 주요시설물·부대시설이 자동으로 켜지지 않습니다(트리의 아이콘으로 필요할 때 켭니다).
  - 좌측 툴바 "전체보기": 등록된 모든 노선(관할 범위)을 지도에 표시하고 범위를 맞춥니다.
  - 트리의 도로 종류 제목(군도 등)을 누르면 그 종류의 등록된 노선 전부를 지도에 표시합니다(GET /api/sections/all-geoms?grade=군도).
  - 서버 코드(routes/sections.js)가 바뀌었으므로 서버 재시작이 필요하고, 화면 파일은 node server/build-dist.js 로 다시 만듭니다.
  - 지도 맞춤(구간·노선·전체보기·도로 종류 클릭)은 한 함수(fitMapToExtent)로 통일: 맞추기 직전 지도 크기를 다시 재고, 사이드바 전환으로 크기가 바뀌면 한 번 더 맞추며,
    연달아 누르면 마지막 요청만 반영합니다(늦게 도착한 응답이 지도를 되돌리지 않음).

26. 도면 다시 올릴 때 중복 처리 (같은 구간 + 같은 파일 이름 = 중복)
  - 예전: [개별 올리기]는 같은 파일이 그대로 쌓였고, [자동 인식 올리기]는 말없이 덮어쓰며 예전 파일을 영구 삭제했습니다.
  - 지금: 새 도면은 바로 등록하고, 이미 같은 이름이 있는 파일은 uploads/_pending-uploads/<토큰>/ 에 따로 빼 두어 기존 파일을 건드리지 않습니다.
    화면에서 "교체할지" 묻고, [확인]이면 기존 파일을 uploads/_import-trash/ 로 보관하며 교체합니다(일괄등록 이력에 "도면 교체" 한 건으로 남아
    "이 등록 취소"로 되돌릴 수 있음 — 가장 최근 등록만 취소 가능). [취소]이면 새 파일을 버립니다. 답하지 않은 보관본은 하루 뒤 자동 삭제됩니다.
  - API: POST /api/routes/files, /api/routes/files/auto 가 중복을 { duplicate }/{ duplicates, pendingToken } 으로 알려주고,
    POST /api/routes/files/pending/resolve { tokens, action: 'replace'|'discard' } 로 처리합니다.
  - 일괄등록(납품 폴더) 경로는 원래부터 같은 구간+같은 이름을 교체(예전 파일 보관·되돌리기 가능)하므로 그대로입니다.
  - 이미 쌓여 있는 중복(같은 구간+같은 이름 2건)은 개발 PC에 1쌍(테스트 노선 담순로의 6형_수치지도데이터.dwg, 시군구 12790)이 있었고 자동 삭제하지 않았습니다.
